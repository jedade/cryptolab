ECIES — Integrated Encryption Scheme

Chiffrement hybride asymétrique Léger Bitcoin · Smart contracts

📖 1. Présentation

Normalisé
ANSI X9.63, ISO/IEC 18033-2, IEEE 1363a, SECG SEC 1
Famille
IES + variante elliptique = ECIES
Type
Chiffrement asymétrique léger

ECIES (Elliptic Curve Integrated Encryption Scheme) est un schéma de chiffrement hybride compact, standardisé dans les années 2000. Là où on combinerait manuellement ECDH + KDF + AES + MAC, ECIES encapsule tout dans une primitive normalisée. Très utilisé dans Bitcoin (messages chiffrés entre nœuds), les smart contracts Ethereum, l'IoT (Hyperledger), et toute situation où l'on veut chiffrer pour un destinataire dont on connaît seulement la clé publique elliptique.

⚙️ 2. Fonctionnement

ECIES has five encryption steps:

1. Bob generates an ephemeral pair (r, R = r·G) — basis of forward secrecy
2. Compute shared secret: S = r · pubAlice (ECDH)
3. Derive: (k_enc, k_mac) = KDF(S)
4. Encrypt: c = AES(k_enc, message)
5. Authenticate: tag = HMAC(k_mac, c)
→ Bob sends (R, c, tag) to Alice

Alice side (decryption):

1. Alice computes S = privAlice · R (inverse ECDH)
2. Derives (k_enc, k_mac) with same KDF
3. Verifies HMAC(k_mac, c) == tag  — reject if mismatch
4. Decrypts m = AES⁻¹(k_enc, c)

💡 ECIES is exactly the "hybrid E2E encryption" pattern documented in Implementations — except that pattern is standardized and named.

">

ECIES suit cinq étapes côté chiffrement :

1. Bob génère une paire éphémère (r, R = r·G) — base de la forward secrecy
2. Calcul du secret partagé : S = r · pubAlice (ECDH)
3. Dérivation : (k_enc, k_mac) = KDF(S)
4. Chiffrement : c = AES(k_enc, message)
5. Authentification : tag = HMAC(k_mac, c)
→ Bob envoie (R, c, tag) à Alice

Côté Alice (déchiffrement) :

1. Alice calcule S = privAlice · R (ECDH inverse)
2. Dérive (k_enc, k_mac) avec le même KDF
3. Vérifie HMAC(k_mac, c) == tag  — rejette si KO
4. Déchiffre m = AES⁻¹(k_enc, c)

💡 ECIES est exactement le pattern "chiffrement hybride E2E" documenté dans la page Implémentations — sauf que ce pattern est standardisé et nommé.

Variantes : ECIES-KEM (Key Encapsulation Mechanism — séparation du chiffrement clé / message), ECIES-DEM (Data Encapsulation Mechanism). Courbes typiques : secp256k1 (Bitcoin), P-256 (web), Curve25519 (moderne).

💻 4. Code

# pip install eciespy
from ecies import encrypt, decrypt
from ecies.utils import generate_eth_key

# Génération d'une paire de clés (style Ethereum)
sk = generate_eth_key()
sk_hex = sk.to_hex()
pk_hex = sk.public_key.to_hex()

# Chiffrement avec la clé publique
message = b"Message confidentiel pour Alice"
ciphertext = encrypt(pk_hex, message)
# Le ciphertext contient : R (clé publique éphémère) + IV + tag + chiffré

# Déchiffrement avec la clé privée
recovered = decrypt(sk_hex, ciphertext)
print(recovered)  # b"Message confidentiel pour Alice"

from cryptography.hazmat.primitives.ciphers.aead import AESGCM

import os

alice_sk = generate_private_key(SECP256K1())
alice_pk = alice_sk.public_key()

ephemeral = generate_private_key(SECP256K1())

key = HKDF(hashes.SHA256(), 32, None, b"ECIES").derive(shared)

) + nonce + ct)

🌍 5. Cas réel : avantages, inconvénients, failles

✅ Avantages
  • Standard ouvert (ANSI, ISO, IEEE, SECG)
  • Léger : un seul appel API pour chiffrer/déchiffrer
  • Forward secrecy avec clé éphémère
  • Compact (~140 octets overhead pour secp256k1)
  • Compatible IoT / smart contracts
⚠️ Inconvénients
  • Implémentations divergent (paramètres KDF, MAC, AES mode)
  • Pas IND-CCA2 sans variante ECIES-KEM
  • Manque parfois de l'AAD ajoutable d'AES-GCM seul
  • Moins répandu que les patterns ad-hoc (PGP, age)
💥 Failles connues
  • Diff. interop entre implémentations (curve, KDF, MAC) → erreurs
  • Mauvais KDF (ANSI X9.63 KDF) historiquement faible vs HKDF
  • Sans MAC, malléabilité totale → toujours utiliser ECIES standard
  • Side-channel sur ECDH si implémentation non constante
  • Shor (quantique) : casse ECDH → migration hybride avec Kyber
