Montgomery, Curve25519 & X25519

Courbe elliptique ECDH Signal · WireGuard · TLS 1.3

📖 1. Pourquoi une autre forme ?

Les courbes de Weierstrass courte (y² = x³ + ax + b) sont la forme historique des courbes elliptiques, mais elles ont deux défauts en pratique :

  • Cas spéciaux (point à l'infini, doublement vs addition) ⇒ branches conditionnelles ⇒ side-channels
  • Multiplication scalaire coûteuse, validation du point obligatoire

Peter Montgomery (1987) introduit une forme alternative : By² = x³ + Ax² + x. Avec elle vient la Montgomery ladder, un algorithme de multiplication scalaire intrinsèquement résistant aux side-channels (timing, cache, power) car le nombre d'opérations est constant indépendamment du bit traité.

En 2006, Daniel J. Bernstein publie Curve25519 : une courbe de Montgomery soigneusement choisie pour ECDH, accompagnée d'une justification publique de chacun de ses paramètres (« nothing-up-my-sleeve »). Le protocole d'échange de clés associé est X25519 (RFC 7748).

⚙️ 2. Forme & paramètres de Curve25519

y² = x³ + 486662·x² + x   (mod 2²⁵⁵ − 19)
A = 486662  ·  B = 1  ·  p = 2²⁵⁵ − 19 (Mersenne-like)
Generator x = 9  ·  Ordre = 8 · ℓ, ℓ = 2²⁵² + 27742317777372353535851937790883648493
Prime 2²⁵⁵ − 19

Réduction modulaire très efficace (proche de 2^k).

A = 486662

Plus petit A > 2 tel que A² − 4 n'est pas un carré → empêche les attaques d'isogénie.

Cofacteur 8

Géré par le « clamping » → pas de petit sous-groupe exploitable.

🪜 3. La Montgomery ladder

Pour calculer k·P, on lit les bits de k du plus haut au plus bas. À chaque bit, on effectue exactement les mêmes opérations qu'on swap deux registres ou non :

R0 = O (point à l'infini)
R1 = P
for bit in k (MSB → LSB):
    if bit == 0:
        R1 = R0 + R1      ; addition différentielle
        R0 = 2 · R0       ; doublement
    else:
        R0 = R0 + R1
        R1 = 2 · R1
return R0
💡 Astuce-clé : les deux branches font 1 add + 1 double. Implémenté avec une sélection conditionnelle (cmov) sans branchement, le temps d'exécution est indépendant de la clé → résistance side-channel intrinsèque.
⚙️ Spécificité Montgomery : on travaille sur la coordonnée x seulement (x-only ECDH). On gagne en performance car y se retrouve modulo signe — non nécessaire pour ECDH.

🧮 4. X25519 — protocole ECDH

Alice : a aléatoire 32 octets → clamp → A = X25519(a, 9)
Bob : b aléatoire 32 octets → clamp → B = X25519(b, 9)
Clé partagée K = X25519(a, B) = X25519(b, A)

Le « clamping » consiste à zéroter les 3 bits de poids faible (cofacteur 8) et fixer les bits 254-255. Cela évite plusieurs classes d'attaques (small subgroup, top-bit timing).

💻 6. Code

# pip install cryptography
from cryptography.hazmat.primitives.asymmetric.x25519 import X25519PrivateKey
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.kdf.hkdf import HKDF
from cryptography.hazmat.primitives import hashes

alice_priv = X25519PrivateKey.generate()
bob_priv   = X25519PrivateKey.generate()

shared_alice = alice_priv.exchange(bob_priv.public_key())
shared_bob   = bob_priv.exchange(alice_priv.public_key())
assert shared_alice == shared_bob   # ✓

# TOUJOURS passer par un KDF avant utilisation
key = HKDF(algorithm=hashes.SHA256(), length=32, salt=None, info=b'session').derive(shared_alice)

# Signature : utiliser Ed25519 (forme Edwards de la même courbe)
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey
sk = Ed25519PrivateKey.generate()
sig = sk.sign(b"message")
sk.public_key().verify(sig, b"message")
// Web Crypto (navigateur récent)
const alice = await crypto.subtle.generateKey({ name: 'X25519' }, true, ['deriveBits']);
const bob   = await crypto.subtle.generateKey({ name: 'X25519' }, true, ['deriveBits']);

// Alice dérive avec la clé publique de Bob
const sharedAlice = await crypto.subtle.deriveBits(
  { name: 'X25519', public: bob.publicKey },
  alice.privateKey,
  256
);

// Bob dérive avec la clé publique d'Alice
const sharedBob = await crypto.subtle.deriveBits(
  { name: 'X25519', public: alice.publicKey },
  bob.privateKey,
  256
);

// Comparaison
const a = new Uint8Array(sharedAlice);
const b = new Uint8Array(sharedBob);
console.log(a.every((v, i) => v === b[i]));  // true

🌍 7. Adoption

✓ Partout
  • Signal Protocol (X3DH)
  • WireGuard (identité + handshake)
  • TLS 1.3 (group X25519, hybride avec Kyber depuis 2024)
  • OpenSSH ed25519/x25519
  • Tor v3 onion services
  • Age, Noise framework
⚠️ Points d'attention
  • X25519 n'est PAS authentifié : combiner avec signature ou PSK
  • Toujours passer par HKDF avant chiffrement
  • Cassé par Shor → migration hybride X25519 + ML-KEM
  • Distinguer X25519 (ECDH) et Ed25519 (signatures)

💥 Failles & attaques connues

Vulnérabilités spécifiques, attaques connues, cassures historiques.

Mauvaise implémentation du clamping

Sans clamping correct des 3 bits faibles, attaques small-subgroup possibles.

Mauvais RNG pour les clés éphémères

Une clé prévisible casse l'échange (et avec lui forward secrecy).

Twist attack si point non validé

Bernstein conçoit X25519 pour être robuste, mais une mauvaise réimplémentation peut casser.

Algorithme de Shor (quantique)

Casse Curve25519/Ed25519 → migration hybride Kyber/Dilithium dès maintenant.
