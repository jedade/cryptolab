🛡️ AES-256-GCM

Symétrique AEAD · standard mondial depuis 2001

📖 Contexte

AES-GCM (Galois/Counter Mode) est la primitive cryptographique qui sous-tend HTTPS, le Wi-Fi (WPA2/3), les VPN, les disques chiffrés, les messageries E2E. Elle réalise deux choses en même temps : chiffrement (confidentialité) ET authentification (intégrité + origine). Un octet altéré dans le chiffré est détecté et rejeté — impossible d'altérer silencieusement.

En interne : AES chiffre un compteur incrémenté par bloc de 16 octets (mode CTR), puis un Galois Hash calcule un tag d'authentification de 128 bits qui dépend de la clé, du chiffré, de l'IV et des données associées optionnelles (AAD).

🎯 Quand l'utiliser

  • Chiffrer des tokens, cookies, payloads stockés en base de données
  • Communications chiffrées quand AES-NI est disponible (serveur, desktop moderne)
  • Chiffrement de fichiers / disques (LUKS, BitLocker, FileVault utilisent en interne AES-XTS, son cousin)
  • Tous les cas où on a une clé partagée et qu'on veut chiffrer + authentifier

✅ Avantages

  • Ultra-rapide avec AES-NI (~5 Go/s par cœur)
  • AEAD : chiffrement + auth en un seul appel
  • Standardisé partout (NIST, IETF, FIPS)
  • Parallélisable (basé sur CTR)
  • NSA approuvé jusqu'au TOP SECRET en 256 bits

⚠️ Inconvénients

  • Lent sans AES-NI (mobile, embarqué) → préférer ChaCha20
  • Limite 2³² blocs par (clé, IV) avant risque de réutilisation
  • Pas de forward secrecy seul — nécessite échange éphémère
  • Implémentations software vulnérables aux attaques timing-cache

💥 Failles connues

  • Réutilisation de nonce : 2 chiffrés avec même (clé, IV) → récupération de clé
  • Forbidden Attack (Joux 2016) : réutilisation de nonce sur TLS
  • Cache-timing sur AES software (Bernstein 2005)
  • Grover (quantique) : AES-128 → 64 bits → AES-256 obligatoire à long terme
  • Tags courts (< 96 bits) permettent forgery

💻 Code de production (Python)

# pip install cryptography
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
import os

# 1. KEY: 32 bytes = 256 bits. Store in a KMS / Vault, never in plain config.
key = AESGCM.generate_key(bit_length=256)
aead = AESGCM(key)

# 2. NONCE: 12 bytes, UNIQUE per (key, message).
#    Random is safe up to ~2^32 messages per key.
nonce = os.urandom(12)

# 3. AAD (associated data): authenticated but NOT encrypted
#    (e.g. metadata, user id, content type — anything that should be bound to ciphertext).
aad = b'user_id=42&type=document'

# 4. ENCRYPT → ciphertext = encrypted_bytes || 16-byte auth tag
plaintext = b'sensitive data'
ciphertext = aead.encrypt(nonce, plaintext, aad)

# 5. DECRYPT → verifies tag before returning. Raises InvalidTag if tampered with.
recovered = aead.decrypt(nonce, ciphertext, aad)
assert recovered == plaintext

# 6. SERIALIZATION pattern: store (nonce || ciphertext) together, key separately.
import base64
token = base64.urlsafe_b64encode(nonce + ciphertext).decode()

🌊 ChaCha20-Poly1305

AEAD alternative · TLS 1.3, WireGuard, Signal

📖 Contexte

ChaCha20-Poly1305 est l'AEAD moderne conçu par Daniel J. Bernstein. ChaCha20 génère un keystream qu'on XOR avec le clair (stream cipher) ; Poly1305 calcule le tag d'authentification. Construit à partir de trois opérations natives CPU (Add-Rotate-XOR), sans tables de lookup → naturellement résistant aux attaques timing-cache et très rapide en software pur.

🎯 Quand l'utiliser

  • Mobile / embarqué / IoT (pas d'AES-NI)
  • TLS 1.3, QUIC, WireGuard, OpenSSH (par défaut)
  • Streaming temps réel (audio/vidéo) — performance constante
  • Partout où on veut résistance side-channel sans aide matérielle

✅ Avantages

  • Rapide sans AES-NI (souvent >1 Go/s software)
  • Construction ARX → résistance cache-timing
  • Pas de tables → code minimal (~100 lignes C lisibles)
  • Brevets libres, design de référence Bernstein
  • Standardisé RFC 8439

⚠️ Inconvénients

  • Plus lent qu'AES sur CPU avec AES-NI (serveur)
  • Nonce 96 bits : aléa pur risqué au-delà de ~2³² messages
  • Moins répandu dans les systèmes anciens / accélérateurs matériels

💥 Failles connues

  • Réutilisation de nonce : casse totale — XOR de 2 chiffrés = XOR de 2 clairs
  • ChaCha20 brut (sans Poly1305) : pas d'intégrité → forgery triviale
  • Grover (quantique) : 128 bits de sécurité quantique (comme AES-256)
  • Aucune cassure pratique connue sur la primitive complète en 2026

💻 Code de production (Python)

from cryptography.hazmat.primitives.ciphers.aead import ChaCha20Poly1305
import os

key   = ChaCha20Poly1305.generate_key()   # 256 bits
nonce = os.urandom(12)                    # 96 bits — keep unique per key
aead  = ChaCha20Poly1305(key)

ct = aead.encrypt(nonce, b'payload', associated_data=b'header')
pt = aead.decrypt(nonce, ct, associated_data=b'header')

# For random nonces in high-volume scenarios, prefer XChaCha20-Poly1305
# (192-bit nonce, no collision worry):
# pip install pynacl
from nacl.secret import SecretBox
box = SecretBox(key)
encrypted = box.encrypt(b'payload')     # 192-bit nonce auto-managed, no collision risk
recovered = box.decrypt(encrypted)

🔑 RSA-OAEP & RSA-PSS

Asymétrique · encore dominant dans les certificats et systèmes legacy

📖 Contexte

RSA est l'algorithme asymétrique le plus largement déployé. On l'utilise aujourd'hui avec deux paddings sûrs : OAEP pour le chiffrement (évite les rejeux et faiblesses connues du "RSA brut") et PSS pour la signature (plus robuste que l'ancien PKCS#1 v1.5). Utilisé dans les certificats TLS, les JWT, S/MIME, signature de code, SSH.

Ne JAMAIS utiliser RSA brut (sans padding) : une longue liste d'attaques dévastatrices (Bleichenbacher, Coppersmith, Manger…).

🎯 Quand l'utiliser

  • Certificats X.509 (encore très demandés)
  • Signature JWT en interopérabilité (alternative à ECDSA/Ed25519)
  • E-mail chiffré (PGP/GPG, S/MIME)
  • Systèmes legacy où ECC n'est pas supporté
  • Quand il faut absolument du support des bibliothèques anciennes

💡 Pour un nouveau projet, préfère Ed25519 (signature) et X25519 (échange de clé) — plus petits, plus rapides, plus simples.

✅ Avantages

  • Support universel (toutes bibliothèques)
  • Éprouvé depuis 47 ans
  • Normalisé : PKCS#1, X.509, JWS
  • Déploiement PKI bien établi

⚠️ Inconvénients

  • Lent (~1000× plus lent qu'AES)
  • Clés grosses : 3072 bits = minimum NIST depuis 2024
  • Signatures grosses (256-384 octets)
  • Complexe à implémenter sûrement (padding, side-channels)
  • Ne peut chiffrer que de petits messages (taille clé − overhead)

💥 Failles connues

  • Bleichenbacher (1998) : oracle de padding PKCS#1 v1.5 → récupération clé privée serveur
  • ROBOT (2017) : résurgence Bleichenbacher sur F5, Citrix, Cisco
  • Coppersmith : petit e + même m → récupération
  • ROCA (CVE-2017-15361) : clés faibles Infineon TPM/smartcard
  • Manger (2001) : attaque timing sur OAEP déchiffrement
  • Shor (quantique) : cassure instantanée de toute clé RSA

💻 Code de production (Python)

from cryptography.hazmat.primitives.asymmetric import rsa, padding
from cryptography.hazmat.primitives import hashes, serialization

# === Key generation (slow: ~1s for 3072 bits) ===
priv = rsa.generate_private_key(public_exponent=65537, key_size=3072)
pub  = priv.public_key()

# === Asymmetric encryption with OAEP-SHA256 ===
# Max plaintext size for 3072-bit key: ~318 bytes. Usually used to wrap an AES key.
session_key = os.urandom(32)
ciphertext = pub.encrypt(
    session_key,
    padding.OAEP(
        mgf=padding.MGF1(algorithm=hashes.SHA256()),
        algorithm=hashes.SHA256(),
        label=None
    )
)
recovered = priv.decrypt(ciphertext, padding.OAEP(
    mgf=padding.MGF1(algorithm=hashes.SHA256()),
    algorithm=hashes.SHA256(),
    label=None))

# === Signature with PSS (preferred over PKCS#1 v1.5 in 2026) ===
signature = priv.sign(
    b"message to sign",
    padding.PSS(
        mgf=padding.MGF1(hashes.SHA256()),
        salt_length=padding.PSS.MAX_LENGTH
    ),
    hashes.SHA256()
)
pub.verify(
    signature, b"message to sign",
    padding.PSS(mgf=padding.MGF1(hashes.SHA256()), salt_length=padding.PSS.MAX_LENGTH),
    hashes.SHA256()
)

# === Serialization (PEM, encrypted) ===
pem_priv = priv.private_bytes(
    serialization.Encoding.PEM,
    serialization.PrivateFormat.PKCS8,
    serialization.BestAvailableEncryption(b"strong_passphrase")
)

🪜 X25519 + Ed25519

Asymétrique moderne · Signal, WireGuard, SSH, TLS 1.3 par défaut

📖 Contexte

X25519 effectue un échange de clés Diffie-Hellman sur la courbe elliptique Curve25519. Ed25519 est le schéma de signature associé (EdDSA). Les deux reposent sur la même courbe publiée par Daniel J. Bernstein en 2006 — conçue avec des constantes "nothing-up-my-sleeve", résistante aux side-channels par construction, ultra-rapide.

Pourquoi ce duo domine en 2026 : clés de 32 octets (vs 384 pour RSA), signatures de 64 octets (vs 384 pour RSA), simple à utiliser sûrement, 10-100× plus rapide que RSA. Utilisé par Signal, WhatsApp, WireGuard, SSH, signature de commits Git, services onion Tor v3.

🎯 Quand l'utiliser

  • Choix par défaut pour tout nouveau projet nécessitant de l'asymétrique
  • X25519 : échange de clés (remplace DH)
  • Ed25519 : signatures numériques (remplace RSA-PSS, ECDSA)
  • Infrastructure clé publique pour SSH, Git, JWT
  • Messagerie E2EE (Signal Protocol = X25519 + Ed25519 + AES-GCM/ChaCha20)

✅ Avantages

  • Clés (32 o) et signatures (64 o) minuscules
  • 10-100× plus rapide que RSA-3072
  • Signatures déterministes (pas d'aléa risqué à la signature)
  • Résistant side-channel par construction (Montgomery ladder)
  • Constantes transparentes (pas de suspicion NSA)

⚠️ Inconvénients

  • X25519 n'est PAS authentifié (combiner avec signature)
  • Pas encore supporté par tous les PKI/TPM corporate
  • Distinguer X25519 (ECDH) vs Ed25519 (signature) — confusion facile
  • Support Web Crypto API récent (2023-2024)

💥 Failles connues

  • Aucune cassure connue sur la primitive elle-même en 2026
  • Mauvaises implémentations : oubli du clamping → attaques small-subgroup
  • Mauvais RNG sur clé éphémère → récupération de clé (cf. PS3 ECDSA disaster)
  • Shor (quantique) : casse ECDH et EdDSA → migration hybride avec Kyber/Dilithium
  • Twist attacks : seulement si implémentation non conforme à la spec

💻 Code de production (Python)

from cryptography.hazmat.primitives.asymmetric.x25519 import X25519PrivateKey
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey
from cryptography.hazmat.primitives.kdf.hkdf import HKDF
from cryptography.hazmat.primitives import hashes

# === ECDH key exchange with X25519 ===
alice = X25519PrivateKey.generate()
bob   = X25519PrivateKey.generate()

# Each party computes the shared secret using the other's public key
shared_alice = alice.exchange(bob.public_key())
shared_bob   = bob.exchange(alice.public_key())
assert shared_alice == shared_bob

# ALWAYS derive a usable key via HKDF — never use raw DH output
session_key = HKDF(
    algorithm=hashes.SHA256(),
    length=32,
    salt=None,                          # or a unique per-session salt
    info=b'app-name session-key v1'     # context binding
).derive(shared_alice)

# Now use session_key with AES-GCM or ChaCha20-Poly1305 to encrypt messages.

# === Digital signature with Ed25519 ===
sk = Ed25519PrivateKey.generate()
signature = sk.sign(b"hello world")      # 64 bytes, deterministic
sk.public_key().verify(signature, b"hello world")
# Raises InvalidSignature on bad signature or tampered message.

🤝 Chiffrement hybride E2E

Le pattern du monde réel · ce que PGP, TLS, age, Signal font sous le capot

📖 Contexte

L'asymétrique est lent et limité (~318 octets par RSA-3072 OAEP). Le symétrique est rapide mais nécessite des clés partagées. Le chiffrement hybride combine les deux : on génère une clé symétrique aléatoire, on chiffre le message avec (rapide), puis on chiffre cette clé avec la clé publique du destinataire. Le destinataire déchiffre la clé symétrique, puis déchiffre le message.

Bonus avec ECDH : des clés éphémères donnent la forward secrecy — même si la clé long-terme du destinataire fuit plus tard, les messages passés restent sûrs.

🎯 Quand l'utiliser

  • Chiffrer un fichier/message pour un destinataire précis (seule sa clé publique suffit)
  • Messagerie end-to-end (Signal, WhatsApp font ça par message)
  • Chiffrer documents dans le cloud (on ne sait pas qui déchiffrera quand)
  • age, PGP, S/MIME, handshake TLS — tous suivent ce pattern

✅ Avantages

  • Vitesse du symétrique + flexibilité de l'asymétrique
  • Aucun secret pré-partagé requis
  • Forward secrecy avec DH éphémère
  • Multi-destinataires : chiffrer la clé pour N destinataires

⚠️ Inconvénients

  • Plus complexe que symétrique pur (plus d'étapes à rater)
  • Nécessite distribuer/valider des clés publiques (problème PKI)
  • Non authentifié par défaut : nécessite signature ou clé de signature

💥 Failles connues

  • EFAIL (2018) : malléabilité PGP/S-MIME si pas d'auth
  • MITM sur clés publiques : distribuer / vérifier l'empreinte correctement
  • Padding oracle si on mélange RSA-PKCS#1v1.5 et vieux TLS
  • Mauvais KDF : ne jamais utiliser la sortie DH brute comme clé

💻 Code de production (Python)

"""
Complete pattern: Alice encrypts a message for Bob, who has only published an
X25519 public key. Bob can decrypt with his private key.
"""
from cryptography.hazmat.primitives.asymmetric.x25519 import X25519PrivateKey, X25519PublicKey
from cryptography.hazmat.primitives.ciphers.aead import ChaCha20Poly1305
from cryptography.hazmat.primitives.kdf.hkdf import HKDF
from cryptography.hazmat.primitives import hashes, serialization
import os

def encrypt_for(recipient_pub_bytes: bytes, message: bytes) -> bytes:
    # 1. Generate an EPHEMERAL X25519 key — basis of forward secrecy
    eph = X25519PrivateKey.generate()
    eph_pub = eph.public_key().public_bytes(
        serialization.Encoding.Raw, serialization.PublicFormat.Raw)

    # 2. ECDH with recipient's public key → shared 32-byte secret
    recipient_pub = X25519PublicKey.from_public_bytes(recipient_pub_bytes)
    shared = eph.exchange(recipient_pub)

    # 3. HKDF to derive the actual encryption key
    key = HKDF(hashes.SHA256(), 32, None, b'hybrid v1').derive(shared)

    # 4. AEAD encryption with a fresh random nonce
    nonce = os.urandom(12)
    ct = ChaCha20Poly1305(key).encrypt(nonce, message, associated_data=None)

    # 5. Final payload: ephemeral pubkey || nonce || ciphertext
    return eph_pub + nonce + ct

def decrypt_for(priv: X25519PrivateKey, payload: bytes) -> bytes:
    eph_pub = X25519PublicKey.from_public_bytes(payload[:32])
    nonce   = payload[32:44]
    ct      = payload[44:]
    shared  = priv.exchange(eph_pub)
    key     = HKDF(hashes.SHA256(), 32, None, b'hybrid v1').derive(shared)
    return ChaCha20Poly1305(key).decrypt(nonce, ct, associated_data=None)

# Test
bob = X25519PrivateKey.generate()
bob_pub = bob.public_key().public_bytes(
    serialization.Encoding.Raw, serialization.PublicFormat.Raw)
payload = encrypt_for(bob_pub, b"Hello Bob, from Alice")
print(decrypt_for(bob, payload))   # b'Hello Bob, from Alice'

🔐 Hash de mots de passe — Argon2

Standard OWASP/IETF 2026 · TOUJOURS utiliser, jamais sha256(pw)

📖 Contexte

Stocker un mot de passe en clair ou avec un hash simple (SHA-256) est une faute grave. Argon2id est le standard moderne de hachage de mot de passe, conçu pour être lent à dessein et coûteux en mémoire — frustrant les attaques brute-force par GPU/ASIC.

Principe critique : chaque utilisateur reçoit un sel aléatoire unique mélangé au hash, pour que deux utilisateurs avec le même mot de passe aient des hashes différents (défait les rainbow tables).

🎯 Quand l'utiliser

  • TOUT stockage de mot de passe (login web, OS, password manager)
  • Dériver une clé de chiffrement DEPUIS un mot de passe (chiffrement de fichier)
  • Remplacer le legacy : bcrypt OK, PBKDF2 minimum, sha256() interdit

✅ Avantages

  • Gagnant du PHC (Password Hashing Competition) 2015
  • Memory-hard : GPU/ASIC inefficaces
  • Configurable : temps / mémoire / parallélisme
  • Sel automatique + versioning algorithme intégré au hash
  • Migration facile : check_needs_rehash

⚠️ Inconvénients

  • Lent par design : ~100ms par login (c'est le but)
  • Coût mémoire : ~64 MiB par login → calibrer par serveur
  • Requiert une lib bien tunée (argon2-cffi)

💥 Failles connues

  • sha256(pw) seul : brute force GPU à 100 milliards h/s → cassure instantanée
  • MD5/SHA1 + sel : reste rapide GPU → 10^9 h/s sur RTX 4090
  • Argon2i vs Argon2d : Argon2i seul a des attaques 2016 → utiliser Argon2id
  • Mal configuré : coût trop faible → pas de vraie protection (ex: PBKDF2 1000 iter)
  • Pas de pepper + leak DB : attaquants brute-forcent n'importe quel mot de passe

💻 Code de production (Python)

# pip install argon2-cffi
from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError

# OWASP 2024 parameters (adjust based on RAM/CPU budget per login)
ph = PasswordHasher(
    time_cost=3,         # 3 iterations
    memory_cost=64*1024, # 64 MiB
    parallelism=4,       # 4 threads
    hash_len=32,
    salt_len=16,
)

# === SIGNUP ===
hashed = ph.hash("my_strong_password")
# → store `hashed` in DB. It contains: algorithm, params, salt, hash.
#   No need for a separate salt field.
# Example: $argon2id$v=19$m=65536,t=3,p=4$$

# === LOGIN ===
try:
    ph.verify(hashed, "my_strong_password")     # OK
    # Auto-upgrade if cost parameters have evolved
    if ph.check_needs_rehash(hashed):
        new_hash = ph.hash("my_strong_password")
        # update DB with new_hash
except VerifyMismatchError:
    pass    # wrong password — return generic error, don't reveal "user exists"

# === BONUS: pepper (stored separately from DB, in env or HSM) ===
import hmac, hashlib, os
PEPPER = os.environ['APP_PEPPER'].encode()  # 32+ random bytes, never in DB
def hash_with_pepper(password: str) -> str:
    peppered = hmac.new(PEPPER, password.encode(), hashlib.sha256).hexdigest()
    return ph.hash(peppered)

🧬 HMAC & HKDF

Authentification + dérivation de clé · partout

📖 Contexte

HMAC (Hash-based Message Authentication Code) authentifie un message avec une clé secrète partagée : le destinataire peut vérifier l'intégrité ET l'origine (même clé utilisée). Standardisé par RFC 2104, immunisé contre les attaques de length-extension qui affligent les hashes bruts.

HKDF (HMAC-based Key Derivation Function) dérive plusieurs clés cryptographiques à partir d'un secret. Cas critique : après un échange ECDH, ne jamais utiliser la sortie brute — toujours la passer à HKDF d'abord.

🎯 Quand l'utiliser

  • HMAC : signature de requêtes API (HMAC-SHA256), webhooks, intégrité cookies
  • HMAC : algorithme HS256 de JWT
  • HKDF : dériver une clé de chiffrement depuis un secret partagé DH
  • HKDF : dériver plusieurs clés depuis un maître (chiffrement + MAC + IV-seed)

✅ Avantages

  • Très rapide (juste du hash)
  • Support universel (toute lib, tout langage)
  • Pas de length-extension (contrairement à SHA-256 nu)
  • Sécurité prouvée sous hypothèses standard du hash

⚠️ Inconvénients

  • Symétrique : pas de non-répudiation (qui a la clé peut forger)
  • Le problème de distribution de clé reste
  • Comparaison du tag HMAC en temps constant obligatoire

💥 Failles connues

  • Comparaison naïve (==) : timing attack → utiliser hmac.compare_digest
  • HMAC-MD5 : encore cassé, à éviter dans les nouveaux designs
  • Length-extension : jamais SHA-256(secret||message) brut ; utiliser HMAC
  • HKDF sans info : collisions entre contextes d'usage
  • Sortie HKDF réutilisée chiffrement + MAC : vulnérabilité

💻 Code de production (Python)

from cryptography.hazmat.primitives import hashes, hmac
from cryptography.hazmat.primitives.kdf.hkdf import HKDF
import secrets

# === HMAC-SHA256 ===
key = secrets.token_bytes(32)
h = hmac.HMAC(key, hashes.SHA256())
h.update(b"message to authenticate")
tag = h.finalize()           # 32 bytes

# Verification (uses CONSTANT-TIME comparison automatically)
h2 = hmac.HMAC(key, hashes.SHA256())
h2.update(b"message to authenticate")
try:
    h2.verify(tag)           # Raises InvalidSignature if bad
    # OK
except Exception:
    pass                     # bad MAC — reject

# === HKDF (extract-then-expand) ===
shared = secrets.token_bytes(32)      # e.g. ECDH output
keys = HKDF(
    algorithm=hashes.SHA256(),
    length=64,                         # request 64 bytes
    salt=b"optional salt",             # per-session unique if possible
    info=b"context info per usage"     # binds the derivation to a specific use
).derive(shared)
key_enc, key_mac = keys[:32], keys[32:]   # 2 independent derived keys

# IMPORTANT: never compare MAC tags with `==` — leaks timing.
# In stdlib Python: secrets.compare_digest(tag1, tag2)

🪪 JWT signé Ed25519 (EdDSA)

Authentification d'API moderne

📖 Contexte

JWT (JSON Web Token) est un format de token qui contient des claims (user_id, expiration, scope, etc.) signés par le serveur. Le destinataire vérifie la signature avec la clé publique — pas d'aller-retour BDD à chaque requête. Trois algorithmes de signature se disputent : HS256 (HMAC, secret partagé), RS256 (RSA, asymétrique), EdDSA (Ed25519). EdDSA est le choix moderne : plus sûr, plus rapide, signatures plus petites.

✅ Avantages

  • Stateless : pas de stockage côté serveur
  • EdDSA : signatures 64 octets, très rapide
  • Auto-contenu : claims + signature en un token
  • Standardisé : RFC 7519, RFC 8037 (EdDSA)

⚠️ Inconvénients

  • Révocation difficile (nécessite une blocklist)
  • Ne pas mettre de données sensibles dans les claims (signé mais pas chiffré)
  • Les tokens fuient dans URLs / logs

💥 Failles connues

  • alg=none : attaque célèbre, lib accepte token non-signé
  • Confusion alg (HS256/RS256) : lib utilise clé publique comme secret HMAC
  • kid path traversal : ../../etc/passwd en kid
  • Pas de check 'exp' : tokens éternels
  • Clés RS256 faibles (< 2048 bits) : forgery

💻 Code de production (Python)

# pip install pyjwt cryptography
import jwt
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey
from cryptography.hazmat.primitives import serialization
import time

sk = Ed25519PrivateKey.generate()
pem_priv = sk.private_bytes(
    serialization.Encoding.PEM,
    serialization.PrivateFormat.PKCS8,
    serialization.NoEncryption())
pem_pub = sk.public_key().public_bytes(
    serialization.Encoding.PEM,
    serialization.PublicFormat.SubjectPublicKeyInfo)

# === ISSUE token ===
token = jwt.encode(
    {
        "sub": "user_42",
        "iat": int(time.time()),
        "exp": int(time.time()) + 3600,    # 1 hour
        "scope": ["read:profile"],
    },
    pem_priv,
    algorithm="EdDSA")

# === VERIFY token ===
claims = jwt.decode(
    token,
    pem_pub,
    algorithms=["EdDSA"],     # ⚠ NEVER accept ['none'] or default to anything!
    options={"require": ["exp", "sub"]})
# Raises if signature bad, exp expired, claims missing.

📦 Chiffrement de fichier streaming

Pour gros fichiers (Go) sans exploser la RAM

📖 Contexte

Un fichier de 5 Go ne tient pas en RAM. Solution : chiffrer par chunks, avec un nonce unique par chunk (dérivé d'un counter), et un tag d'authentification par chunk. Le dernier chunk est marqué pour qu'un attaquant ne puisse pas tronquer silencieusement le fichier.

✅ Avantages

  • Mémoire constante (taille chunk)
  • Accès aléatoire (seek au chunk N possible)
  • Intégrité par chunk (détection corruption)
  • Anti-troncature (marqueur dernier chunk)

⚠️ Inconvénients

  • Overhead tag par chunk (16 o) → +0.02% sur chunks 64 KiB
  • Format custom = aucun outil standard ne sait lire
  • Attaque par réordonnancement possible si chunks non liés à leur position

💥 Failles connues

  • Pas de binding counter : attaquant réordonne les chunks
  • Pas de marqueur dernier chunk : attaquant tronque
  • Nonce frais par chunk sans counter : risque collision sur Go
  • Recommandé : utiliser age (https://age-encryption.org), ne pas réinventer

💻 Code de production (Python)

from cryptography.hazmat.primitives.ciphers.aead import ChaCha20Poly1305
import os, struct

CHUNK   = 64 * 1024     # 64 KiB per chunk
TAG_LEN = 16

def encrypt_file(in_path: str, out_path: str, master_key: bytes):
    base_nonce = os.urandom(8)    # 8 fixed bytes + 4 counter bytes = 12-byte nonce
    aead = ChaCha20Poly1305(master_key)
    with open(in_path, 'rb') as fi, open(out_path, 'wb') as fo:
        fo.write(base_nonce)
        counter = 0
        while True:
            chunk = fi.read(CHUNK)
            if not chunk:
                break
            nonce = base_nonce + struct.pack('>I', counter)
            # AAD binds: "is this the last chunk?" → prevents truncation
            is_last = b'\x01' if len(chunk) < CHUNK else b'\x00'
            ct = aead.encrypt(nonce, chunk, associated_data=is_last)
            fo.write(struct.pack('>I', len(ct)) + ct)
            counter += 1

def decrypt_file(in_path: str, out_path: str, master_key: bytes):
    aead = ChaCha20Poly1305(master_key)
    with open(in_path, 'rb') as fi, open(out_path, 'wb') as fo:
        base_nonce = fi.read(8)
        counter = 0
        while True:
            header = fi.read(4)
            if not header:
                break
            (ct_len,) = struct.unpack('>I', header)
            ct = fi.read(ct_len)
            nonce = base_nonce + struct.pack('>I', counter)
            is_last = b'\x01' if (ct_len - TAG_LEN) < CHUNK else b'\x00'
            fo.write(aead.decrypt(nonce, ct, associated_data=is_last))
            counter += 1
